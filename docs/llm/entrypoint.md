# LLM entrypoint

This repository is `humtr/tul`, the Terminal Update Loop runtime.

Start by treating runtime artifacts as facts and repo docs as durable guidance. Do not rely on previous chat memory when the repo files answer the question.

## Runtime baseline

Use the latest uploaded `tul-vf-latest.md` as the runtime baseline. It should show:

- HEAD and Remote HEAD
- release gate result
- working tree state
- fresh clone result when available
- runtime snapshots

When source context is needed, prefer `tul-source-latest.zip` generated by `tul export source` or `tul export`.

## Canonical command surface

The canonical terminal commands are:

```text
tul show
tul package
tul update
tul verify
tul export
tul run
tul clean
tul recover
tul setup
```

No legacy alias layer is part of the canonical design.

Normal user workflow:

```bash
cd ~/prj/tul

tul package
tul run
```

Stepwise workflow:

```bash
tul package
tul update
tul export
tul verify fresh
tul show
```

## Command boundaries

- `tul show` is read-only. Use `tul show exports` for source/review artifact freshness.
- `tul package` shows the newest matching package candidate by default.
- `tul update` applies a package and publishes the repo update.
- `tul verify` is quick/local by default.
- `tul verify fresh` writes uploadable verification artifacts.
- `tul export` creates source and review artifacts.
- `tul run` performs the full Terminal Update Loop.
- `tul clean` is plan-only by default.
- `tul recover` is plan-only by default.
- `tul setup` is status-only by default.

## Package generation rules

When generating a package, use the existing tul package format:

```text
tul-package.yml
README.md
files/
apply.sh
apply.ps1
```

Never use `git add -A`, force push, broad cleanup, or destructive operations in generated packages.

Final package answers should include:

- zip download link
- SHA256
- baseline summary
- changed files
- apply command
- success criteria
